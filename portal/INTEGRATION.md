# Connect the portal to the existing StatLine Gateway

Browser requests go directly to the Gateway. The portal adds no API routes, proxy, account database, enrollment service, or scorer.

## Public configuration

The build defaults to `https://api.statline.dev`. An API URL can be selected without rebuilding in `dist/client/statline-config.js`:

```js
window.STATLINE_PUBLIC_CONFIG = { apiUrl: "http://127.0.0.1:8000" };
```

Preserve a setting through rebuilds in `public/statline-config.js`. An empty `apiUrl` disables live requests. The existing local launcher selects the local API for its session. Credentials must never be included in this file, a public environment setting, generated content, or the static bundle.

A production portal and credentialed API connection need HTTPS. HTTP is supported for localhost. The browser sends credentials only to the configured API, only when the user chooses an operation. Credentialed requests reject redirects.

## Existing service requirements

- Public health: `GET /v4/health`.
- Public contract: `GET /openapi.json`; Swagger and ReDoc remain on the API host.
- Scoring and catalogs: approved bearer API key with `userbase` scope.
- Identity: `GET /v4/auth/whoami`, subject to the Gateway's principal policy.
- Device and device-owned key operations: active enrolled device with valid proof headers.
- Browser CORS: allow the exact portal origins on the existing Gateway process using its existing `STATLINE_PORTAL_ORIGINS` setting. Include Authorization, Content-Type, and the existing X-SL proof headers as required by its policy.

## Playground

Saved examples are actual Python/Gateway/StatPack-verified engine outputs. Selecting a dataset or record does not calculate scores in the browser. Saved mapped rows are generated by the real adapter, and their batch context is identified.

Live mode sends the editable request to the responding Gateway's `score_v4` operation. It requires a reachable health/contract, an approved key, and the Gateway's authorization policy. It displays actual errors and responses. If the deployed source version differs, that difference is shown.

The current Gateway has no anonymous scoring endpoint. Public visitors can inspect saved examples; approved users can score through the existing API. A bearer-only playground cannot satisfy a deployment that additionally requires device proof; use its approved signed client in that mode. No key or new public endpoint is embedded to bypass this constraint.

## Browser privacy and dashboard

The portal never invokes local device permission APIs (USB, Bluetooth, HID,
Serial, camera, microphone, local applications) and never asks users to upload
private keys. The dashboard supports **read-only bearer identity/scopes**;
key management and signed device administration stay in the local CLI.
The public portal accepts **only** `https://api.statline.dev` as a browser API
origin. Only a portal hosted on loopback may opt in to a loopback API. This
prevents public webpages from triggering browser local-network permission
prompts, even with an accidental runtime-config override. No Gateway probes
are performed on page load: the user must click Check API or take a specific
credentialed action. If a Gateway operation requires device proof, the browser
cannot satisfy it and the user must use an approved CLI client.

No API key is stored in localStorage, sessionStorage, cookies, generated files,
or a portal server. A key entered for a request remains in ephemeral page state.

## Availability

Public health and contract checks run **only on user action**. Browser failures
can result from CORS, TLS, connectivity or Gateway downtime; they must not be
presented as proof of a service outage. Source-generated docs, downloads, and
saved examples remain available without an API connection.

The Python Gateway's auth contract remains unchanged. The portal deliberately
exposes fewer administrative features than the CLI.
